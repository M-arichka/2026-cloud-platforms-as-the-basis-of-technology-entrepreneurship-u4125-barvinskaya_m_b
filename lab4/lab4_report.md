# "Разработка инфраструктуры MVP AI приложения."
## Цель работы

Создать прототип AI-приложения с базовой функциональностью: спроектировать инфраструктуру, рассчитать экономическую модель и обосновать выбор облачных ресурсов для трёх стадий жизненного цикла продукта.

## Описание приложения:
**AI-приложение** - Приложение – личный ассистент, подключаемый к мессенджерам и корпоративным чатам (Telegram, и др.). Ассистент читает переписку, участвует в диалогах, ищет информацию, напоминает о встречах, генерирует идеи и оценивает эмоциональный фон собеседников.

**AI-компонент** базируется на большой языковой модели (LLM) через управляемый API Vertex AI (Gemini). Модель обрабатывает контекст, выделяет намерения, генерирует ответы и анализирует тональность. При необходимости подключаются вспомогательные AI-сервисы, но ядром остаётся Gemini.

### Функциональные модули
**Интеграционный шлюз (Bot Gateway)**: приём сообщений от разных платформ, унификация, отправка ответов.

**Оркестратор диалогов:** управление состоянием беседы, вызов AI, краткосрочный контекст.

**AI-движок:** взаимодействие с Vertex AI Gemini и постобработка.

**Модуль напоминаний и планирования:** создание, хранение и активация напоминаний (Cloud Scheduler/Tasks).

**Модуль анализа тональности:** оценка эмоционального окраса (в MVP часть движка, позже может быть отдельным микросервисом).

**Модуль поиска:** поиск во внешних источниках или внутренней базе знаний.

**Хранилище данных:** профили пользователей, история, контекст, напоминания.

### Ожидаемые нагрузки по стадиям:
- Стадия 1 (MVP):1–5 пользователей, ~500–1000 сообщений/сутки, 2-3 одновременные сессии.
- Стадия 2 (тестирование партнёрами): 50–200 пользователей, ~10 000 сообщений/сутки, до 50 одновременных сессий.
- Стадия 3 (продакшн): 500–5000 пользователей, 50 000+ сообщений/сутки, до 500 одновременных сессий

### Стадия 1 — MVP (до 100 пользователей)
**Цель:** максимально дёшево запустить рабочий прототип, подтвердить гипотезу, получить первую обратную связь. Только serverless-сервисы Google Cloud без постоянных ресурсов. Единый контейнер на Cloud Run содержит все модули, Firestore для состояния, Vertex AI API, Cloud Scheduler.

| Компонент GCP | Назначение | Конфигурация | Тип	Обоснование |
|---|---|---|---|
| Cloud Run |	Единый backend: вебхуки, оркестрация, вызов AI | 1 vCPU, 512 МБ, max instances=5 | Serverless, масштабируется до нуля, простота |

### Стадия 2. Тестирование партнёрами (до 1000 активных пользователей)
**Цель:** подключить первых партнёров, проверить нагрузку, начать собирать данные для AI-рекомендаций. Важно не потерять партнёров из-за нестабильности.
**Вычислительные ресурсы:**\
Миграция на контейнеры (ECS Fargate или GCP Cloud Run с собственными образами).\

Добавляется постоянный сервис Core Orchestrator, способный держать открытые соединения (WebSocket при необходимости).\

Автоскейлинг от 1 до 3 задач.\

**LLM:** Продолжаем использовать API, но с резервированием пропускной способности (provisioned throughput) для гарантированной задержки. Анализируем среднюю стоимость на запрос.\

**Векторное хранилище**: Переход на управляемое Pinecone (Standard pod) или развёртывание Qdrant на отдельной небольшой ВМ. Всё ещё недорого.

**Очередь:** SQS с выделенной пропускной способностью или переход на RabbitMQ внутри ECS для снижения задержек.

**Redis:** Обязателен, хранит контекст диалога (до 30 минут на пользователя), что резко снижает повторные вызовы LLM.

**База данных:** RDS PostgreSQL на маленьком инстансе (db.t3.medium) с Multi-AZ для надёжности.

**Дополнительно:**
Модуль оценки тональности реализуется как отдельная Lambda (или вызов LLM с коротким промптом).
Внедряется мониторинг с алертами (CloudWatch Alarms).

Расходы: ~300–700 $/мес в зависимости от числа активных пользователей и объёма токенов.

### Стадия 3 - Продакшн (5000 пользователей, высокие нагрузки)
**Вычислительная платформа:**
Kubernetes (EKS/GKE) с отдельными нодами для CPU-задач и GPU-нодами для инференса LLM.
**Микросервисная архитектура:**

ingress-svc – приём вебхуков, маршрутизация.

orchestrator – ядро логики (stateful, хранит long-term memory).

rag-svc – поиск по векторной базе.

evaluator – оценка состояния (использует отдельную малую LLM или BERT-модель на CPU).

scheduler – менеджер напоминаний (CronJob + Durable Execution).

**LLM-инференс:**
Self-hosted решение на GPU-инстансах (A10G/A100). vLLM/TGI для высокоскоростного обслуживания.
Динамическое масштабирование нод с GPU при пиковой нагрузке.
Параллельно сохраняется возможность fallback на внешний API для отказоустойчивости.

**Векторное хранилище:**
Кластер Qdrant или Milvus на Kubernetes, либо fully-managed Pinecone с высокими throughput limits.

**Очередь:** Apache Kafka (MSK / Confluent) для гарантированной доставки и перемотки событий.

**Кэш / сессии:** Redis Cluster с персистентностью.

**База данных:** RDS Aurora PostgreSQL Serverless v2 – эластичное масштабирование под переменную нагрузку.

**Хранилище:** S3 для логов, бэкапов и артефактов моделей.

**Мониторинг и observability:** Prometheus, Grafana, Loki (или ELK), OpenTelemetry-трейсинг.

**Безопасность:** VPC с приватными сабнетами, WAF на границе, шифрование всех данных, аудит доступа.
